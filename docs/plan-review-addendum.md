# 对《Colugo 0.28.2 开发方向与迭代实施建议》的评审与补充

> **立场**：方向同意 —— 缺口确实在"用电池写规则"，而不在"再多几个预设"。
> **依据**：本仓库 0.28.2 源码，不是进度报告。所有行号指向 `runtime/src/` 与 `gh/Colugo/`。
> **用途**：开会前替换掉三处会被人当场问倒的说法，再补四条实施建议。

---

## 1. 先纠正三处事实

这三处不影响方向判断，但会直接影响会上对"还剩多少活"的估计。

| 原文说法 | 代码实际 | 证据 |
|---|---|---|
| Entity 有六种预设行为 | **只有一种**：`follow-curve`。`drift / orbit / attract / repel / follow-pointer` 在 v0.15 已删除 | `entity.js:73-76`，`BEHAVIORS = ['follow-curve']` |
| `mask` / `blend` 均仅透传 | **`blend` 是真合成的**（`globalCompositeOperation`），只有 `mask` 是空字段 | `renderer2d.js:207`；`svg.js:98` 对 mask 写警告 |
| `Signal to Float` 有 100ms 推动机制，被当成主循环风险 | 100ms 是 **GH 侧取样节拍**，不是运行时帧率；浏览器的绘制是逐帧的 | `StatTicker.cs:20`；`main.js:100` 有轨道就每帧重画 |

补充两点原文没写、但会影响工作量的：

- **实体是确定性的**：分布 `u = (i / count + phase) % 1`，没有随机、没有 seed（mulberry32 已在 v0.15 删除），模拟按 1/60 定步长。原文 §5 设想的"力/阻尼/分裂"不是加参数，是给一个确定性系统开一个不确定的口子。
- **进度报告里"六种行为"这条是我写错了**（当时引用的是协议文档而非代码），已同步修正。开会请以本页为准。

## 2. 这条路线其实已经走了 60%

原文把 Runtime Expression 写成"首要新增能力"，容易让人以为是从零起一套求值器。实际已有的东西比看上去多：

```js
// signal.js:98 —— 现在就在用的求值入口
export function signalValue(sig, time)   // 纯函数：定义 + 时间 → 数值
```

- 它是**确定性**的（同一 t 同一值），已经被 64 项运行时断言覆盖；
- 定义由 GH 下发（`BridgeServer.PublishSignal`，约 100 字节 @30Hz），浏览器只存定义不采样；
- 目前唯一的消费者是 `sendStat()` 里的 `signalSnapshot(signals, clock.time)` —— **10Hz、只回传、不参与渲染**。

所以 R1 的真实工作量是两件事：

1. 把 `kind` 分支换成 AST 求值（算法结构不变，`switch` 换 `eval(ast, ctx)`）；
2. 把消费者从"回传 GH"扩成"也能落到渲染属性"。

**这不是新建子系统，是给已有的纯函数加一个渲染侧出口。** 建议会上这样定调，比"新增 Runtime Expression 模块"更能反映真实成本。

## 3. 四条实施建议（与原文不同的做法）

### 3.1 绑定不要新增 op，先塞进 `cmd.upsert`

原文建议 `binding.upsert / binding.remove` 独立 op。我建议先走 `cmd.upsert` 内嵌：

```js
cmd = { id, geom, style, opacity, ..., bind: { opacity: <ast>, 'style.width': <ast> } }
```

理由是可复用性，不是省事：

- **解析/序列化各加一处**：`normalizeCmd()`（`doc.js:39`）收字段，`serializeCmd()`（`exporter.js`）发字段 —— 两处机械改动，其余全部复用；
- **增量与快照免费**：`snapshot:true`、断线重连、`doc.reset` 都不用为绑定写第二套恢复逻辑；
- **独立 HTML / 序列导出不用新逻辑**：`serializeDoc()` 逐条走 `serializeCmd`，字段带上就跟着作品一起走；
- 绑定的生命周期天然跟指令一致 —— 指令没了绑定就该没。

对照一下：如果新增 `binding.upsert`，就要自己解决"快照时先发 cmd 还是先发 binding""重连后绑定如何重建""指令删除时绑定谁清"，这三件事现在由 doc 的既有机制免费处理。

代价是同一属性的绑定更新会连带整条 cmd 重发（几十字节），在 30Hz 求解节拍下可忽略。
等将来绑定需要独立于指令增删（比如一份表达式绑多条指令且单独改），再拆 op 不迟 —— 那时也知道该拆成什么样。

### 3.2 有一个坑必须提前说：重绘判定

`main.js:100` 用 `hasTracks(doc)` 决定"要不要每帧重画"：

```js
if (doc.time !== undefined && hasTracks(doc)) dirty = true;
```

只加绑定、不改这里，表现是**数值在变、画面不动**（因为 `dirty` 一直是 false）。这类 bug 很难从现象反推原因。
实现时必须做成 `hasTracks(doc) || hasBindings(doc)`，并在验收里单独占一条。

### 3.3 绑定求值只写进绘制局部变量，不改 `cmd` 本体

`renderer2d.js` 每帧都读 `st.width` 画线（`g.lineWidth = st.width`），所以绑定只要在**取样式那一刻**求值即可，成本 = 一次函数调用。

但如果把结果写回 `cmd.style.width`，导出、SVG、下一帧的 diff 都会拿到被污染的脏值。规则写死：**cmd 是静态真值，绑定结果只活在 draw 的局部变量里。**

### 3.4 首批只绑三个属性，`progress` 放第二批

建议顺序：`opacity` → `style.width` → `entity.size`。

`draw.progress` 看起来最诱人（`fract(t/duration)` 的循环生长），但它同时被 `Draw Progress`、track 的 `reveal`、tween 三处影响，**得先定义谁覆盖谁**才能绑。先绑前三个就够做出"曲线呼吸"的演示；绑 progress 之前要先做一次语义澄清。

## 4. 对 Behavior 的建议：第一版只做"只读状态"

原文 §5 的 Behavior Graph 是方向正确的，但第一版范围偏大 —— 它要求"状态写回"，而现有实体系统是**确定性、定步长、无随机**的（见 §1）。一旦允许用户写状态：

- 导出 PNG 序列要能复现 → 必须固定步长 + 输入回放 + 检查点；
- 断线重连要能续 → 得定义状态是恢复、重置还是续播；
- 现有回放断言（`replay-csharp` 15 项、`replay-3d` 6 项）的前提就是"同样输入得到同样结果"，会被打破。

**建议把 R2 拆成两步：**

- **R2a（只读）**：把 `entity.age / u / speed / count` 作为 `Runtime Input` 暴露给表达式。用户能写"按年龄变色、按 u 调速、按速度调线宽" —— 这类需求在创作里占大头，且**不引入任何不确定性**，两三天可完成。
- **R2b（可写）**：`State Update / Condition / Spawn`，配套固定步长回放与状态检查点。到这一步再谈"自定义弹簧"。

原文 §5.5 的验收作品（自定义弹簧粒子）建议放到 R2b，不要作为 R2 的完成定义 —— 否则 0.30 会因为一个不确定性设计卡住整个节奏。

## 5. 对 Mark 的建议：编译期展开，不要新开渲染协议

原文 §6.2 说"Mark 的输出仍编译成现有 DrawCommand"，这点我完全同意，值得再往前推一步：

- **Mark 不新增 op**，在 GH 侧就展开成 `geom.upsert` + `cmd.upsert`（点描就是 points 几何，短划就是短折线，图章就是同一几何的多条 cmd 带不同 transform）；
- 好处：快照、增量、SVG、导出、图层全部零改动；
- 代价是 patch 体积 —— 5000 个 mark 大约几百 KB。所以**验收里要加一条体积指标**（例如单次 patch < 512KB），否则"五种静态画法"很容易把 WebSocket 打爆。

真正需要新增的只有 `Style Map`（属性 → 视觉参数）这类**编译期**电池，它本身不进运行时。

## 6. 两处优先级我不同意

**① `Draw Path` 收敛 10 输入不该是 P0。**
改端口 = 破坏所有现存 `.gh`，而它跟表达层没有依赖关系。建议：先加一个**可选** `Style` 输入（旧 10 个端口一个不动），新定义走新写法，收敛放到 R3 和 `Drawing Style` 一起做。把 P0 让给"清屏策略"和"绑定白名单"，那两件才是真的有前置依赖。

**② 3D 的 1.5 秒硬编码不该压到 P3。**
`scene3d.js:412` 写死 `u = (this._time / 1.5) % 1`。任何一次演示里，三维动画和二维轨道都会**对不上拍子**，这是当场会被看见的问题。
最便宜的修法不是接 Track，而是给 `Transform 3D` 加一个 `Duration` 输入（默认 1.5，行为不变）：C# 加端口、`xform` 带上时长、`scene3d` 读它替掉魔数 —— 三处小改，半小时内能验。完整接 Track 仍可留在 P3。

## 7. 验收再加三条硬指标

原文 §11 的验收已经很严，补三条**能一句话证明"没走 GH 求解"**的：

1. **空闲时 patch 字节 = 0**（已有能力，回归即可）；
2. **绑定生效期间 `doc.rev` 不变，但画面在动** —— 这条最直接，任何人看一眼 HUD 就能判断真假；
3. **确定性对齐**：导出序列第 n 帧 == 实时播放到 `t = n/fps` 的帧，逐像素比较。

另外补两条实现纪律：

- **表达式禁止读 `performance.now()` / `Date.now()`**，时间只能来自 `clock.time`。否则离线导出与实时播放会漂，而且这种漂移只在导出时暴露。
- **`serializeCmd()` 要同步带上 `bind`。** 顺带说一个现存问题：`track` 会被完整序列化，但 `morph` 没有（`exporter.js:21-48` 无 morph 字段），所以**当前用 morph 做的作品导出独立 HTML 后是静态的**。表达式如果只加在运行时、没进序列化，会重演同一个问题 —— 这类"实时能看、导出就死"的缺口，建议在 R1 里一次性补齐，并加一条导出回放断言。

## 8. 一句话口径（开会用）

> R1 不是新引擎，是把 `signal.js` 里那个已经跑通的 `value(定义, t)` 从"四个写死的公式"扩成 AST，再把结果从"只回传 GH"改成"也能直接改渲染属性"；顺便补上重绘判定和确定性时间两条纪律。
