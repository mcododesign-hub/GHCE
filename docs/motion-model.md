# 指令与运动模型（cmd = 一次绘图函数调用）

> 写于 v0.12.0。回答两个问题：**cmds 到底是什么**、**不是仿射的运动该怎么表达**。

## 1. cmd 就是 Processing 里的一次函数调用

```processing
// Processing
stroke(#E8E6DF); strokeWeight(1.5); noFill();
pushMatrix(); translate(120, 80); rotate(radians(45)); scale(1.2);
beginShape(); vertex(...); vertex(...); endShape();
popMatrix();
```

GHCE 里同一件事被拆成一条 `cmd`：

| Processing 里 | GHCE 里 | 谁给的 |
|---|---|---|
| `stroke() / fill()` | `cmd.style` | `Stroke Style` / `Fill Style` 电池 |
| `pushMatrix / translate / rotate / scale` | `cmd.transform` | `Transform` 电池（每条指令一个矩阵） |
| `beginShape / vertex` | `cmd.geom` | `Path Input`（采样后的点缓冲） |
| `popMatrix` 之后的层级 | `cmd.layer` | `Layer` 电池 |
| `while (millis() < ...)` | `cmd.track` / `cmd.osc` | `Timeline` / `Oscillator` |
| `mousePressed()` 分支 | `cmd.events` | `Event Trigger` 电池 |
| `draw()` 里算的那一帧 | 浏览器每帧求值 | 运行时 |

所以 **cmds 是"绘图调用的参数集合"**，全部参数都由 GH 原生电池组合而来 —— 你不需要写代码，
但你得到的仍然是 Processing 里那种"逐个参数控制一次绘制"的自由度。

一条重要推论：**指令是数据，不是过程**。GH 只说"现在该长什么样"，从不说"这一帧该画什么"。
过程（每帧插值、摆动、事件响应）都在浏览器里，所以 GH 停手之后画面照样动。

## 2. "前面的几何"和"后面的几何"差在哪

```
Curve (世界坐标)
  └─ Path Input ──► geom: 点缓冲（页面坐标，未变换）      ← "前面的几何"
        └─ Draw Path ──► cmd: { geom, style }
              └─ Transform ──► cmd.transform.matrix       ← "后面的几何"的**表示**
```

关键决定：**后面的几何不作为点重算一遍，而是作为"矩阵"记在指令上**。原因有三：

1. **可插值**。点缓冲没法告诉你"从哪来"，矩阵可以和上一次的矩阵插值出中间态 —— 这就是动画。
2. **省带宽**。一个矩阵 6 个数，重算 500 条 × 40 点要 2 万个 float。
3. **改一处不牵连别处**。同一个 geom 可以被多条指令引用，各自套不同矩阵。

所以"前后差异"在协议里只有两种落地方式：

- `transform.matrix`（+ `progress`，由过渡引擎写）：差异是**仿射**的
- `deform`（逐点位移，v0.13 计划）：差异是**非仿射**的

## 3. 运动分三层，先说清你手里的一个效果属于哪层

| 层 | 这个层能表达什么 | 协议表示 | 每条指令成本 | 能否插值 | GH 里怎么搭 |
|---|---|---|---|---|---|
| **T1 仿射** | 平移 / 旋转 / 缩放 / 斜切 / 镜像 | `matrix` 6 个数 | 6 float | ✅ TRS 分解后插值 | `Transform` 电池（`Move`/`Rotate`/`Scale`/自写矩阵） |
| **T2 场映射** | 逐点位移：噪声抖动、磁铁、扭曲、沿法线膨胀、参数化变形 | `deform` 逐点向量（f32 base64） | 2 float / 点 | ✅ 两组向量线性插值 | 原生电池算出向量列表 → `Displace` 电池 |
| **T3 结构变化** | 顶点数变了：布尔运算、subdivision、合并/分裂、重新采样 | 新 geom + 换引用 | 整套新缓冲 | ❌ 无法插值 | 任何改变几何拓扑的电池 |

判断口诀：**点位不变 → T1；点位变但点数不变 → T2；点数或顺序变 → T3。**

### T3 为什么插不了，以及怎么绕过

两条曲线做布尔，结果是另一条曲线，点数和参数化都不同 —— 没有"中间形状"这个东西。
可用的三种绕过方式（都不属于插值）：

1. **淡入淡出**：旧几何 `opacity 1→0`，新几何 `0→1`，交叉替换（最常用，看起来像"变形"）
2. **参数化重建**：别做布尔，改成一个连续参数 `t` 的公式（例如 fillet 半径 0→1），点数和顺序不变，于是降级为 T2/T1
3. **粒子中介**：把两端都采样成一个固定数量的点集，在点集之间插值（画面会"散开再聚拢"）

**设计上的建议**：想让它动，就别让它换拓扑。GH 里凡是输出曲线/曲面并改变结构的运算，
默认都是 T3；把它们当成"新镜头"，而不是"同一个东西在动"。

## 4. 复杂函数映射到底怎么定义（T2）

Processing 里你会这么写：

```processing
for (int i = 0; i < pts.length; i++) {
  PVector p = pts[i];
  float n = noise(p.x * 0.01, p.y * 0.01, t);
  vertex(p.x + cos(n * TAU) * 20, p.y + sin(n * TAU) * 20);
}
```

GHCE 里**不要**在浏览器里写这个公式 —— 浏览器不该知道你作品的具体算法。改成本地算好、只传结果：

```
Path Input → (PDeform? 点缓冲) → [原生电池：每个点算一个偏移向量]
                                        ↓
                                  Displace 电池
                                        ↓
                                  cmd.deform = [dx0,dy0, dx1,dy1, ...]
                                        ↓
                       运行时：vertex(p + deform[i] * progress)
```

这样做的三个后果，都是想要的：

- **带宽可控**：500 点 = 2000 个 float = 8 KB，比 60 Hz 重发几何便宜一个数量级
- **可插值**：上一次的向量组和这一次的插值，就是"场在慢慢变"
- **算法自由**：GH 里噪声/吸引子/FFT/任何你能连出来的东西都能当向量场，运行时不需要认识它们

GH 侧最小约定（`Displace` 电池的端口）：`Paths`（点缓冲）+ `Vectors`（与点数相同的二维向量列表）
→ `Paths`。点数不匹配时报 Warning 并退化成恒等，不会静默画错。

数据规模上限：单条路径建议 ≤ 2000 点；超过时向量场本身就比几何贵，改回 T1 或用 T3 的换镜头。

## 5. 现在这一版（v0.14）落在哪

- T1 完成：每条指令一个矩阵，`Transform` 按序对应；GH 只发终态，浏览器自己把变化演出来
  （`runtime/src/tween.js`，默认 0.9 s）。**第一次出现从原始状态演**，之后从"此刻画面上的位置"演，
  所以连续拖动是平滑跟随。没有 Field、没有 progress 输入 —— GH 怎么变，画面就怎么变。
- T1 的锚点是**从矩阵里解出来的**，不需要额外输入：`C = (I − A)⁻¹·τ`（不动点）。
  你在 GH 里用什么中心转，它就绕什么中心转。
- T2 未做：协议字段名先定成 `deform`，`Displace` 电池未实现
- T3 未做：目前只能靠切换指令（等于换镜头），交叉淡入还没做

### 5.1 loop 与 `void draw()`

`Timeline` 删除后没有播放头了。先把物理事实摆清：**60 fps 的循环，意味着那个值一秒要被产出 60 次。**
只有两个地方能产出它。

| 谁产出 | 怎么做 | 实际帧率 | 状态 |
|---|---|---|---|
| **GH 逐帧解算** | 原生 `Timer`（`Params › Util`，`GH_Timer`）输出 elapsed → 你的表达式 → `Transform` | 受 GH 解算速度限制，通常 10–30 Hz，画面台阶式 | **已可用**：间隔 < 120 ms 时引擎直通，不叠缓动 |
| **浏览器本地时钟** | 一段循环烘焙成 N 帧矩阵，浏览器在帧之间插值并循环 | 60 fps | 未实现，需协议扩容（一条指令收一串矩阵） |

第一种就是 `void draw()` 的字面翻译：GH 每解算一次 = 一次 `draw()` 调用，`Timer` 的 elapsed 就是
`millis()/1000`。它唯一的问题是 GH 解算没那么快。第二种能到 60 fps，且**仍然没有 Field、没有预设曲线** ——
N 帧全是你在 GH 里用 `Series` 喂同一套表达式算出来的，浏览器只负责播。

在第二种落地之前，要在 GH 里做周期运动，用 `Timer` + 原生数学（`sin` / `Modulus`）就够，
别指望它丝滑；要丝滑就得等烘焙序列。

## 6. 一张对照表：你想要的效果 → 该用哪层

| 想要 | 层 | 做法 |
|---|---|---|
| 方块各自转 45° / 放大 / 挪位 | T1 | `Transform`（每条一个 `Xform`），改了就自动演 |
| 一条线像水波一样起伏 | T2 | 向量场 = `sin(x*k + phase) * amp`，`phase` 由 `Timer` 或自己抬的数值驱动 |
| 噪声抖动（手绘感） | T2 | `noise(点坐标)` → 向量场，幅度小、频率高 |
| 所有点被鼠标吸引 | — | v0.15 已删：`Entity Behavior` 的 6 个预设只保留"沿路径"，这类效果要做就自己写 |
| 圆逐渐变成花瓣 | T2 | 逐点法向偏移，`offset` 随时间 0→1 |
| 两条曲线求并集 | T3 | 交叉淡入，或改写成参数化重建 |
| 一条线分裂成两条 | T3 | 同上；或两条都先存在，用 `reveal` 分别画出来 |
| 笔画一点点画出来 | 已有 | `Draw Progress` / `style.reveal` |
| 颜色 / 透明度呼吸 | T1' | GH 里随时间给值（`Timer` → `sin` → 表达式），浏览器过渡过去；`Field` 那套已删 |
